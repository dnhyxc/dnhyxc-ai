# 专题实现文 — 改动前 / 改动后代码对比

专题实现文（`docs/<功能域>/*.md`）中的**关键代码**须以**对比**形式呈现，让读者无需对照 `git diff` 即可看出「哪里变了」。细则与 `SKILL.md` 硬约束 §2、工作流 §3 一致；本文件为格式与取材的展开说明。

## 1. 基本原则

| 原则 | 说明 |
| ---- | ---- |
| **同粒度成对** | 某函数 / 方法 / hook / 组件 / 配置块发生改动时，文档中须**改动前 + 改动后**成对展示，覆盖**同一完整符号**（例如完整的 `function A` 或完整的 `const x = useMemo(…)`，而非只贴 diff 里的三行或仅函数体内 `if`）。符号边界见 `code-symbol-scope.md`。 |
| **与 diff 对齐** | 对比内容须来自本轮锁定的 `git diff` / `git show` / PR；不得臆造「改动前」版本。 |
| **讲解注释在两侧** | 改动前、改动后块均须 **100% 逐行上方详细注释**（`code-line-comments.md`）；禁止只注释关键行或 diff 行。 |
| **不适用产品姊妹稿** | `project-guide.md`、`project-update-info.md` 及四套 TS 姊妹数据**不做**代码前后对比。 |

## 2. 「改动前」版本如何取材

按优先级（与 SKILL 工作流 §1 一致）：

1. **未提交改动**：`git diff <path>` 中 `-` 行侧；或 `git show HEAD:<仓库相对路径>` 取工作区基线（通常为最近一次提交）。
2. **已提交、多 commit**：`git show <parent>:<path>` 或 `git diff <base>...HEAD -- <path>`。
3. **用户粘贴的 diff**：直接还原 `-` / `+` 两侧。
4. **全新文件（纯新增）**：无「改动前」— 见 §4。
5. **整文件删除**：无「改动后」— 见 §4。

行号标注：改动前块写**基线版本**大致行号（来自 `git show` 时）；改动后块写**当前源码**大致行号。

## 3. 推荐 Markdown 结构（默认格式）

每个**发生改动的逻辑单元**一组对比；单元之间用 `###` 小节（模块 / 符号名）。

```markdown
### 4.x `resolveUrl` 函数

**对比范围**：`packages/bar/src/url.ts` 中 `resolveUrl` 全函数（摘录时上下用 `// ...` 保留未改上下文）。

**改动前**（基线：最近一次提交，约 L42–L58）

```typescript
// 旧版 resolveUrl，仅接受单个 input 字符串
function resolveUrl(input: string) {
  // 已是 http 开头则直接返回，不处理相对路径
  if (input.startsWith('http')) return input;
  // 其余情况原样返回，相对路径可能导致资源 404
  return input;
}
```

**改动后**（当前源码，约 L42–L65）

```typescript
// 新增可选 base，用于拼接站点内相对路径
function resolveUrl(input: string, base?: string) {
  // 完整 URL 仍直接返回，与旧版行为一致
  if (input.startsWith('http')) return input;
  // 有 base 且非根路径开头时，与 base 做 join
  if (base && !input.startsWith('/')) return join(base, input);
  // 无 base 或以 / 开头时原样返回
  return input;
}
```

**变更摘要**（可选，一两句）：参数增加 `base`；相对路径走 `join`，修复子路径资源加载失败。
```

### 3.1 标注要求

- **改动前** / **改动后** 小标题**必填**（可用粗体 `**改动前**` / `**改动后**`）。
- 每个代码块正上方仍须**来源行**（路径 + 大致位置 + 版本说明），与 SKILL §2 一致；对比组内前后两块**各自**标注，不得省略。
- **变更摘要**：建议写在对比组末尾，用 prose 点出 diff 焦点（删/增/改的行或行为），避免读者在两段等大块里自己找差异。

### 3.2 大函数 / 大组件如何摘录

- 未改动的首尾上下文：两侧**对称**使用相同位置的 `// ...（未改动）`，保证读者对齐阅读。
- **禁止**只贴「改动后」而把「改动前」换成纯文字描述（除非 §4 例外）。
- 若 diff 仅改函数内数行：两侧仍展示**完整符号**（声明行 + 签名 + 足够上下文 + 闭合），使差异行在上下文中可见。
- **禁止**仅贴函数体 / `useMemo` 回调内部 / 孤立 `return { … }` 而无 `const foo = useMemo` 等外壳（见 `code-symbol-scope.md` §3 反例）。

### 3.3 `useMemo` / `useCallback` 摘录示例

小节标题 `thoughtListQuoteActions` 时，须含完整 memo 符号：

```typescript
const thoughtListQuoteActions = useMemo(() => {
  // … 回调体内逐行注释 …
  return { /* … */ };
}, [ /* deps */ ]);
```

不得从 `if (!cluster) return null` 起笔而缺少 `const thoughtListQuoteActions = useMemo(() => {`。

## 4. 例外（仅展示一侧）

| 情况 | 文档写法 |
| ---- | -------- |
| **纯新增**文件或符号 | 只写 **改动后**；来源行注明「新增」；正文一句说明「基线中不存在」。 |
| **纯删除** | 只写 **改动前**；注明「已删除」及删除动机。 |
| **仅改 import / 重命名** | 仍成对展示 import 块或符号声明；若整文件仅换路径，可成对展示文件顶部 import 区。 |
| **格式化 / 无语义 diff** | 可合并为一句「仅格式化，逻辑无变」，**可不**展开成对代码块（须在 §2 改动范围中说明）。 |

## 5. 与「仅贴最新代码」的边界

- **错误**：只贴当前仓库最新实现 + 文字说「以前是这样」。
- **正确**：读者在同一小节内看到两段可 diff 的代码，差异行在相同结构下对齐。

## 6. Agent 自检（对比专项）

- [ ] 每个在 diff 中有实质改动的函数 / 组件片段是否都有**成对**前后块？
- [ ] 前后块是否**同一完整符号**（声明→闭合，见 `code-symbol-scope.md` §6）？
- [ ] 是否误将函数体 / hook 回调内部当作完整摘录？
- [ ] 「改动前」是否来自 git 基线而非猜测？
- [ ] 纯新增 / 纯删除是否按 §4 处理并显式标注？
- [ ] 大段摘录时两侧 `// ...` 是否对称，便于肉眼 diff？
- [ ] 前后块是否均已 **100%** 逐行注释（`code-line-comments.md` §8），含 `}`、参数行、链式中间行？
