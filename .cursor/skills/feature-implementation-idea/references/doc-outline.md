## 4. 方案比对与最终方案

先写候选和比对，**最后**才写 §4.4。禁止先写 §4.4 再倒填候选。

总体方案走完 4.1～4.4。每个还会改变架构、数据流或状态归属的决策，在 §4.5 各走一遍同样结构（六块不可缺）。只有总体一个分叉时，§4.5 写「无其他会改变架构、数据流或状态归属的决策」。

### 4.1 候选方案

至少 2 个，且都能落地。优先包含「直接复用现状」。每个候选写清能工作的做法，禁止稻草人。

#### 方案 A：<名称>（复用 / 扩展 / 新增）

- **做法**：模块、入口、数据放哪、谁调用谁（具体到路径或现有函数）
- **能工作的原因**：…
- **主要代价**：…

#### 方案 B：<名称>

- **做法**：…
- **能工作的原因**：…
- **主要代价**：…

（有方案 C 则同样写全）

### 4.2 比对

同一维度，单元格写事实（复用哪个文件、多几次往返、哪条失败路径没盖住）。没有差别写「此项相同」，不适用写「不适用」，不要留空。

| 维度 | 方案 A | 方案 B |
|------|--------|--------|
| 正确性（失败路径、边界、数据是否会错） | … | … |
| 复用 / 与现状契合 | … | … |
| 改动面（要动哪些路径） | … | … |
| 复杂度（新概念、新状态、新依赖） | … | … |

| 风险（迁移、互斥、并发、回滚） | … | … |
| 可维护性（以后改一处还是改多处） | … | … |

### 4.3 综合考量

用一段短文写清，不要只复述表格：

- 本需求里哪几个维度权重大，为什么（扣 §1 约束和 §3 已有能力）
- 选定哪一个，它在高权重维度上赢在哪
- **明确放弃**落选方案的哪一项优点（例如少一次请求、少一张表），以及为什么这个优点抵不过短板

### 4.4 最终方案

六块都要写，不能用「见上文」代替。

#### 背景

做这个决定时面对的缺口和硬约束（用 §2 / §3 的事实重写 3～6 句，让本节单独可读）。

#### 具体思路

从缺口推到做法，按顺序写：

1. 模块怎么切（UI / Hook / Utils / API / DB），哪块复用、哪块新增
2. 数据从哪来、到哪去
3. 状态放哪（MobX / useState / URL / 服务端 / DB），为什么不放在另一层
4. 关键边界怎么处理（失败、重复提交、互斥、空数据）

## 9. 具体实现（主链路代码）

规则：

- 单块只覆盖一条路径：一个关键函数、一段数据契约，或一处调用点
- 块首用注释标明 `对应 §4.4 步骤 n`
- 每一行非空、非纯花括号上方注释「做什么 + 为什么」，见 [`code-line-comments.md`](code-line-comments.md)
- 禁止整文件粘贴，禁止与该决策无关的样板
- 代码表达的是打算怎么写，不是已合并 diff 的前后对照
