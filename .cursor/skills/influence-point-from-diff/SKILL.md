# 改动影响点分析（influence-point-from-diff）

## 目标

把**当前一轮改动**整理成可归档的**影响面分析**，回答两件事：

1. **是否影响原有功能需求** — 逐项对照既有能力，给出 **是 / 否 / 有条件变化** 及理由。
2. **影响点具体有哪些** — 模块 × 场景矩阵、潜在风险、未改动项、回归清单。

**落盘**：`docs/Influence-point/<文件名>.md`（见 § 文件名规则）。**默认不改业务源码**。

## 与相近 Skill 的边界

| Skill | 侧重点 | 输出目录 |
|-------|--------|----------|
| **本 Skill** | 对**既有功能**的波及与回归 | `docs/Influence-point/` |
| `implementation-doc-from-diff` | 改动**如何实现**、前后代码对比 | `docs/<功能域>/` |
| `code-review` | 正确性 / 安全 / 性能审查 | 聊天回复，不落盘 |
| `feature-implementation-idea` | 未实现的规划方案 | `docs/ideas/` |

同一轮改动可同时触发本 Skill 与 `implementation-doc-from-diff`：**两篇分工不同**，文首「延伸阅读」互链，**禁止**把影响矩阵整段复制进实现思路专题。

## 硬约束

1. **白名单路径**：仅新建或更新 `docs/Influence-point/**/*.md`；可更新 [`docs/Influence-point/README.md`](../../../docs/Influence-point/README.md) 索引表。**不得**改 `apps/**`、`packages/**` 等，除非用户明确要求。
2. **结论以源码为准**：分析须通读 diff 涉及文件及**调用方**；文末固定句：**（若与仓库最新源码不一致，以源码为准）**。
3. **阅读约定**（写入文首或 §1 脚注）：「历史风险」指旧实现曾出现的问题，不代表现行代码仍会触发。
4. **一主题一文件**：一轮含多个**独立**改动主题时，各写一篇；禁止把互不隶属的主题堆进同一正文。
5. **语言**：正文简体中文；路径用仓库相对路径便于跳转。

## 何时启用

- 「写影响点分析 / Influence-point / 影响面」
- 「这次改动会不会影响 XXX / 原有功能 / 回归范围」
- 「分析 diff 的波及点并写入 docs」
- 用户 `@docs/Influence-point` 并要求分析当前改动

## 工作流（按顺序）

### 1) 锁定改动事实来源

按优先级：

1. 用户粘贴的 `git diff` / `git show` / PR 描述
2. 用户 `@` 的文件 + 「以这些为准」
3. 会话内已落地且用户确认的路径
4. 若无范围：并行 `git status` + `git diff`，列出候选文件并向用户确认（若仍模糊则按 diff 继续，文内注明假设范围）

记录：**改动文件表**（路径 + 一句话变更摘要）。

### 2) 还原「原有功能需求」基线

在写结论前，必须建立**对照清单**（写入文档 §1「分析目的」）：

1. **产品/规格文档**：`docs/ebook/`、`docs/ideas/`、`apps/frontend/specs/`、`docs/ebook/developer/` 等与改动域相关的说明；grep 改动符号名、模块名。
2. **调用链**：对 diff 中导出符号、hook 返回值、组件 props 用 `codegraph_callers` / `Grep` 找**全部**调用方；标注对外 API 是否变更。
3. **并存能力**：同一 UI 入口、互斥关系（如听书 vs 听当前）、共享 DOM 层（marks-pane / listen overlay）是否仍隔离。
4. **数据与 sync**：是否触及 annotation sync、持久化、SSE、MobX store。

**禁止**仅凭 diff 行数猜影响；**必须**至少核对一层调用方或规格描述。

### 3) 逐项判定「是否影响原有功能」

对每个**既有能力**（来自 §2 清单）给出判定：

| 判定 | 含义 |
|------|------|
| **否** | 行为、API、DOM 边界与改前一致 |
| **是** | 破坏、移除或改变用户可感知语义 |
| **有条件变化** | 主路径不变，特定条件下行为不同（须写清条件） |
| **低 / 无** | 仅增强、性能微变、或仅开发体验 |

汇总为 **结论摘要表**（维度 | 是否影响 | 说明），放在 §1 末尾。

### 4) 展开影响点细节

按 [`references/doc-outline.md`](references/doc-outline.md) 骨架撰写，**至少包含**：

- **§2 改动要点**：相对改前行为（文字流程或短代码块）；写清动机
- **§3 影响点矩阵**：模块/场景 × 影响等级 × 分析（等级：无 / 低 / 中 / 高）
- **§4 潜在风险与缓解**：风险 | 等级 | 说明 | 建议验证
- **§5 未改动项**：明确「刻意不动」的边界，避免误报回归
- **§6 回归清单**：可勾选 `- [ ]` 项，覆盖互斥、边界、sync、布局
- **§7 相关文档滞后**（若有）：规格/姊妹稿与改后行为不一致的路径

影响等级定义：

- **无**：代码路径未触达或逻辑等价
- **低**：增强、文案、极边缘降级
- **中**：体验变化、性能可感知、需产品确认
- **高**：数据丢失、功能不可用、越权、必现 bug

### 5) 文件名与落盘

**目录**：`docs/Influence-point/`

**文件名规则**（kebab-case，**3～5 个语义段**，总长建议 ≤ 40 字符）：

- 格式：`<域>-<能力/对象>-<动作或主题>.md`
- **域前缀**：与产品能力一致，如 `epub-`、`chat-`、`cos-`
- **动作词**：`extraction`（抽取）、`consolidation`（合并）、`relayout`（重排）、`vs-annotations`（层间隔离）等
- **禁止**：`analysis`、`report`、`doc`、`change`、`update` 等空泛词；禁止日期戳；禁止一句英文句子

**好例**：`epub-quote-listen-player-bar.md`、`epub-mark-shared-extraction.md`

**差例**：`change-analysis-2026.md`、`epub-listen-refactor-impact-report.md`

**标题**（H1）：`# <产品能力> — 影响点分析`（可略长于文件名）

### 6) 更新索引

1. 在 [`docs/Influence-point/README.md`](../../../docs/Influence-point/README.md) 表格**新增一行**：链接 | 一句话范围（与现有行风格一致）。
2. 若存在对应的 `docs/ebook/` 或 `docs/<域>/` 实现专题，在其「延伸阅读」补链到本篇（**只加链接**，不重写实现文）。
3. **不必**改 `docs/README.md`（Influence-point 已在总索引）；除非用户要求全库索引同步。

### 7) 落盘前自检

- [ ] §1 含**分析目的**、**改动范围表**、**结论摘要表**
- [ ] 每个「是/有条件变化」结论有**调用链或源码证据**（路径或符号名）
- [ ] §3 矩阵行数 ≥ 改动触达的独立场景数
- [ ] §6 回归项可手工执行、无实现细节依赖
- [ ] 文件名通过 §5 规则；README 已登记
- [ ] 未修改白名单外源码

## 输出模板

落盘正文结构见 [`references/doc-outline.md`](references/doc-outline.md)。新建文件时**复制骨架再填**，勿省略 §5「未改动项」与 §6「回归清单」。

## 多功能拆分

与 `implementation-doc-from-diff` §7 同标准：可独立命名、独立验收、路径集合几乎不相交的改动 → **各一篇** Influence-point 文；README 各登记一行。

可选：极短 `changelog-YYYY-MM.md` 只列链接，**不得**重复粘贴各篇矩阵。
