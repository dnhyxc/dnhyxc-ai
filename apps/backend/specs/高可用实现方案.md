# 高可用（HA）实现方案及具体实现步骤

> 适用范围：为 `dnhyxc-ai` 后端（NestJS 11 + MySQL 8 + Redis + BullMQ + Qdrant + COS + Nginx + PM2）建立高可用架构。  
> 衔接关系：本方案**独立于**`微服务架构实现方案.md` 可先行落地（单体阶段即可用），并作为微服务化后的高可用底座。  
> 落地原则：**单点优先消除，数据零丢失优先于可用性**，每阶段可独立上线、可回滚、可演练。

---

## 1. 目标与范围

### 1.1 SLA 目标

| 等级 | 指标 | 目标值 |
|------|------|--------|
| 可用性 | 年度可用率 | ≥ 99.9%（≈ 年宕机 ≤ 8.76h） |
| RTO | 故障恢复时间 | ≤ 5 min（自动故障转移） |
| RPO | 数据丢失窗口 | ≤ 0（强一致）/ ≤ 1s（缓存层） |
| 响应 | P99 延迟 | ≤ 500ms（CRUD）/ SSE 首字 ≤ 2s |

### 1.2 范围
- ✅ 应用层高可用（无状态化 + 多实例 + 负载均衡 + 优雅关闭）
- ✅ 数据层高可用（MySQL 主从 + 自动切换、Redis 哨兵、Qdrant 集群）
- ✅ 中间件高可用（Nginx 双活、PM2 cluster、BullMQ 持久化）
- ✅ 容灾与备份（全量/增量/binlog/快照/跨区）
- ✅ 弹性能力（限流、熔断、重试、幂等、超时、降级）
- ✅ 监控告警（指标 + 日志 + 链路 + 告警通道）
- ✅ 分阶段落地（H0–H4，含验收清单与故障演练）

### 1.3 非目标
- 不在第一阶段做异地多活（留作 H5 演进）。
- 不引入 Service Mesh（Istio），用 Nginx + 应用内治理先行。
- 不替换 COS（对象存储由云厂商保证 SLA，做跨区复制即可）。

## 2. 现状单点故障分析

逐组件标注**单点风险**与**爆炸半径**，作为本方案改造依据。

| 组件 | 现状（来自 `docker-compose.yml` / `deploy.backend.json`） | 单点风险 | 爆炸半径 |
|------|----------------------------------------------------------|---------|---------|
| 应用进程 | 单机 PM2 单进程 `pm2 start npm --name server` | 进程崩溃=全站不可用 | 全部 |
| Nginx | 单机单实例 | Nginx 挂=入口全断 | 全部 |
| MySQL | `db`(3090) 主库 + `db1`(3092)（多版本路由用，**非主从**） | 主库宕=写不可用、读不可用 | 全部业务 |
| Redis | 单实例（生产 12029，本地无容器） | 缓存失效 + BullMQ 队列丢失 | 队列/缓存全挂 |
| Qdrant | 单实例 6333/6334 | 容器停=知识库检索/入库中断 | 知识库 QA |
| COS | 单桶单区 | 区域故障=图片/电子书不可读 | 文件域 |
| 服务器 | 单台 `101.43.50.15` | 主机宕=所有组件不可用 | 全部 |
| 网络 | 单公网入口 | 端口被封=入口不可达 | 全部 |

> **结论**：当前最大单点是「单机」与「单 MySQL 主库」，本方案优先消除这两类。

## 4. 应用层高可用

### 4.1 无状态化改造（前置条件）
多实例的前提是「任一实例可处理任一请求」，需消除进程内状态：

| 现有进程内状态 | 改造方向 |
|--------------|---------|
| `ChatStreamRegistry`（`chat-stream.registry.ts`，会话内存映射） | 迁移到 Redis（`SET sessionId instanceId`），停止信号广播到所有实例 |
| `EnglishLearningStreamAbortRegistry` | 同上，迁移到 Redis |
| 会话历史内存缓存 | 已用 MySQL 持久化，确认无内存兜底 |
| 文件静态服务（`serveUploadStaticMiddleware`） | 上 COS，本地仅缓存 |

**改造示例**：流式停止信号跨实例广播

```ts
// shared/stream/stream-coordinator.ts
import { Inject, Injectable } from '@nestjs/common';
import { InjectRedis } from '@nestjs/redis'; // 或 ioredis 直连
import Redis from 'ioredis';

@Injectable()
export class StreamCoordinator {
  private pub: Redis;
  private sub: Redis;

  constructor(@InjectRedis() redis: Redis) {
    this.pub = redis.duplicate();
    this.sub = redis.duplicate();
    // 订阅停止频道
    this.sub.subscribe('stream:stop');
    this.sub.on('message', (channel, msg) => {
      if (channel === 'stream:stop') {
        const { sessionId } = JSON.parse(msg);
        // 在本实例中断对应流
        this.abortLocal(sessionId);
      }
    });
  }

  // 任一实例发起停止，所有实例收到
  emitStop(sessionId: string) {
    this.pub.publish('stream:stop', JSON.stringify({ sessionId }));
  }
}
```

### 4.2 PM2 Cluster 模式（H0 即可落地）
当前 `pm2 start npm --name server -- run start:prod` 改为 cluster：

```js
// ecosystem.config.js
module.exports = {
  apps: [{
    name: 'server',
    script: 'dist/src/main.js',          // 直接跑编译产物，不走 npm 包壳
    instances: 'max',                     // = CPU 核数
    exec_mode: 'cluster',
    max_memory_restart: '2G',             // 内存超限自动重启
    env: { NODE_ENV: 'production', PORT: 9112 },
  }],
};
```

> 注意：cluster 模式下端口由 PM2 内部负载，对外仍是单端口 9112。多机时由 Nginx upstream 汇聚。

### 4.3 Nginx upstream 多实例负载
从单机单后端升级为多后端池：

```nginx
upstream backend_pool {
    least_conn;                          # 最少连接（SSE 长连接友好）
    # 健康检查：主动探测
    server 127.0.0.1:9112 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:9112 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:9112 max_fails=3 fail_timeout=30s backup;  # 备用
    keepalive 64;                       # 长连接复用
}

server {
    listen 443 ssl http2;
    # ... TLS 配置

    location /api/ {
        proxy_pass http://backend_pool;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # SSE 流式：关闭缓冲
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;

        # 限流：按 IP 限流，防雪崩
        limit_req zone=api_zone burst=100 nodelay;
    }
}

# 限流区定义
limit_req_zone $binary_remote_addr zone=api_zone:10m rate=20r/s;
```

### 4.4 优雅关闭（零宕机重启）
应用需捕获 `SIGTERM`，停止接收新请求、等待进行中的流式请求完成：

```ts
// main.ts
async function bootstrap() {
  const app = await NestFactory.create<NestExpressApplication>(AppModule);
  app.enableShutdownHooks();   // 已存在

  // 显式优雅关闭：等流式完成
  process.on('SIGTERM', async () => {
    logger.log('SIGTERM received, draining connections...');
    // 停止接受新连接（NestJS + Express 需配合 server.close()）
    await app.close();
    logger.log('All connections drained, exiting');
    process.exit(0);
  });

  await app.listen(process.env.PORT ?? 9112);
}
```

PM2 reload（而非 restart）触发 SIGTERM，配合优雅关闭实现零宕机发布：

```bash
pm2 reload server   # 逐进程 reload，不中断
```

### 4.5 健康检查端点
新增 `/api/health` 供 Nginx 与负载均衡探测：

```ts
// health/health.controller.ts
import { Controller, Get } from '@nestjs/common';
import { HealthCheck, HealthCheckService, TypeOrmHealthIndicator, RedisHealthIndicator } from '@nestjs/terminus';

@Controller('health')
export class HealthController {
  constructor(
    private health: HealthCheckService,
    private db: TypeOrmHealthIndicator,
    private redis: RedisHealthIndicator,
  ) {}

  @Get()
  @HealthCheck()
  check() {
    return this.health.check([
      () => this.db.pingCheck('mysql'),
      () => this.redis.pingCheck('redis'),
    ]);
  }
}
```

Nginx 主动健康检查（需 `nginx_upstream_check_module`）：

```nginx
upstream backend_pool {
    server 10.0.0.11:9112;
    server 10.0.0.12:9112;
    check interval=5000 rise=2 fall=3 timeout=3000 type=http;
    check_http_send "GET /api/health HTTP/1.0\r\n\r\n";
    check_http_expect_alive http_2xx;
}
```

## 5. 数据层高可用

### 5.1 MySQL 高可用（主从 + 自动切换）

#### 5.1.1 拓扑
```
        Orchestrator（仲裁，独立部署）
            │ 监控 + 自动故障转移
   ┌────────┴────────┐
   │                 │
Primary (12009)  Replica1 (12006)  Replica2 (可选拓展)
   │ 异步复制(binlog)
   ▼
```

> 说明：现 `db`(3090) 与 `db1`(3092) 是多版本路由用，**非主从**。HA 需新增真正的复制关系。

#### 5.1.2 主从配置
Primary `my.cnf`：
```ini
[mysqld]
server-id = 1
log_bin = mysql-bin
binlog_format = ROW
gtid_mode = ON
enforce_gtid_consistency = ON
sync_binlog = 1                    # 每次提交刷盘，RPO≈0
innodb_flush_log_at_trx_commit = 1
```

Replica `my.cnf`：
```ini
[mysqld]
server-id = 2
log_bin = mysql-bin
relay_log = relay-bin
gtid_mode = ON
enforce_gtid_consistency = ON
read_only = ON
relay_log_recovery = ON
```

建立复制账号与通道（在 docker-compose 启动后执行）：
```sql
-- Primary 上
CREATE USER 'repl'@'%' IDENTIFIED BY 'repl_pass_strong';
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'repl'@'%';
-- Replica 上
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='primary', SOURCE_USER='repl', SOURCE_PASSWORD='repl_pass_strong',
  SOURCE_AUTO_POSITION=1;
START REPLICA;
```

#### 5.1.3 自动故障转移（Orchestrator）
部署 Orchestrator（独立容器，监控 Primary/Replica）：
```yaml
# docker-compose.ha.yml 片段
orchestrator:
  image: openark/orchestrator:latest
  container_name: dnhyxc_orchestrator
  restart: always
  ports: ["3000:3000"]
  volumes:
    - ./orchestrator/orchestrator.conf.json:/etc/orchestrator.conf.json
  environment:
    - MYSQL_TOPOLOGY_USER=repl
    - MYSQL_TOPOLOGY_PASSWORD=repl_pass_strong
```

故障转移策略（`orchestrator.conf.json`）：
```json
{
  "RecoverMasterClusterFilters": ["*"],
  "MasterFailoverLostInstances": false,
  "FailMasterClusterPromotionIfSQLThreadNotUpToDate": true,
  "PostMasterFailoverProcesses": [
    "/usr/local/bin/notify-failover.sh {failureCluster} {successorHost} {successorPort}"
  ]
}
```

应用连接切换：使用 ProxySQL 或应用层连接池感知拓扑变化。简化方案用 **HAProxy + 健康检查**：

```haproxy
# haproxy.cfg
listen mysql
    bind 0.0.0.0:13306
    mode tcp
    option mysql-check user haproxy
    server primary 10.0.0.11:12006 check inter 2000 rise 2 fall 3
    server replica 10.0.0.12:12006 check inter 2000 rise 2 fall 3 backup
```

应用 `.env` 连接 HAProxy：
```
DB_HOST=10.0.0.10
DB_PORT=13306
```

#### 5.1.4 读写分离（可选，H3）
写走 Primary，读走 Replica。TypeORM 用 `QueryRunner` 区分：

```ts
// shared/db/db-replication.ts
const readConn = new DataSource({ ...config, port: 12006, replication: false });
const writeConn = new DataSource({ ...config, port: 12009, replication: false });
// Service 中：读用 readConn，写用 writeConn
```

> 起步阶段可不分离，故障转移后由 HAProxy 路由到新 Primary 即可。

### 5.2 Redis 高可用（哨兵模式）

#### 5.2.1 拓扑
```
   Sentinel-1   Sentinel-2   Sentinel-3   （3 个哨兵，独立节点）
        │            │            │
   ┌────┴────────────┴────────────┴────┐
   │  Master(6379) ← Slave1(6380) ← Slave2(6381)
```

#### 5.2.2 docker-compose（哨兵集群）
```yaml
redis-master:
  image: redis:7.4
  container_name: redis_master
  restart: always
  command: ["redis-server", "--appendonly", "yes", "--requirepass", "${REDIS_PASS}"]
  ports: ["6379:6379"]
  volumes: ["../redis/master:/data"]

redis-replica-1:
  image: redis:7.4
  container_name: redis_replica1
  restart: always
  command: ["redis-server", "--appendonly", "yes", "--replicaof", "redis-master", "6379", "--masterauth", "${REDIS_PASS}", "--requirepass", "${REDIS_PASS}"]
  ports: ["6380:6379"]

redis-replica-2:
  image: redis:7.4
  container_name: redis_replica2

redis-sentinel-1:

redis-sentinel-2:
  image: redis:7.4
  container_name: redis_sentinel2
  command: ["redis-sentinel", "/etc/redis/sentinel.conf"]
  ports: ["26380:26379"]
  volumes: ["./redis/sentinel2.conf:/etc/redis/sentinel.conf"]

redis-sentinel-3:
  image: redis:7.4
  container_name: redis_sentinel3
  command: ["redis-sentinel", "/etc/redis/sentinel.conf"]
  ports: ["26381:26379"]
  volumes: ["./redis/sentinel3.conf:/etc/redis/sentinel.conf"]
```

`sentinel.conf`（每个哨兵一份，端口递增）：
```

sentinel monitor mymaster redis-master 6379 2    # quorum=2，3 哨兵需 2 票
sentinel auth-pass mymaster ${REDIS_PASS}
sentinel down-after-milliseconds mymaster 5000      # 5s 无响应判下线
sentinel failover-timeout mymaster 30000
sentinel parallel-syncs mymaster 1
```

#### 5.2.3 应用接入哨兵
用 `ioredis` 哨兵模式，自动感知主切换：

```ts
// shared/redis/redis.factory.ts
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import Redis from 'ioredis';

@Injectable()
export class RedisFactory {
  constructor(private config: ConfigService) {}

  createClient(): Redis {
    return new Redis({
      sentinels: [
        { host: 'sentinel-1', port: 26379 },
        { host: 'sentinel-2', port: 26380 },
        { host: 'sentinel-3', port: 26381 },
      ],
      name: 'mymaster',
      password: this.config.get('REDIS_PASS'),
      // 连接池
      maxRetriesPerRequest: 3,
      retryStrategy(times) {
        return Math.min(times * 200, 2000);
      },
    });
  }
}
```

> 现有 `RedisConfigFactory`（`factorys/redis-config.factory.ts`）改为基于哨兵构建。

### 5.4 BullMQ 高可用
- 队列存储在 Redis，复用哨兵集群（5.2）即天然 HA。
- 任务持久化：Redis AOF `appendonly yes` 已开启，故障恢复不丢任务。
- Worker 多实例：每个应用实例都起 Worker，BullMQ 自身保证同任务不被多实例重复消费（visibility timeout）。

## 6. 弹性与容错能力

### 6.1 限流（防雪崩）
保留现有 `express-rate-limit`（300/min），补充按用户与按接口维度：

```ts
// 全局限流
app.use(rateLimit({
  windowMs: 60_000, max: 300,
  standardHeaders: true, legacyHeaders: false,
  message: { statusCode: 429, message: '请求过于频繁，请稍后再试' },
}));

// 关键接口限流（LLM 调用，按 userId）
app.use('/api/chat', rateLimit({
  windowMs: 60_000, max: 20,
  keyGenerator: (req) => (req.user as any)?.id?.toString() ?? req.ip,
}));
```

### 6.2 熔断与重试（调用外部 LLM / 搜索 API）

import { Injectable } from '@nestjs/common';
import { CircuitBreaker } from 'opossum';

@Injectable()
export class LlmCircuitBreaker {
  private breaker: CircuitBreaker;

  constructor() {
    this.breaker = new CircuitBreaker(this.callLlm.bind(this), {
      timeout: 30000,            // 30s 超时
      errorThresholdPercentage: 50,  // 错误率 50% 触发熔断
      resetTimeout: 30000,       // 30s 后半开试探
      rollingCountTimeout: 60000,
      rollingCountBuckets: 6,
    });
    this.breaker.fallback(() => ({ content: '服务暂时不可用，请稍后重试', done: true }));
  }

  async execute(prompt: string) {
    return this.breaker.fire(prompt);
  }

  private async callLlm(prompt: string) {
    // 实际 LLM 调用，失败自动计入熔断统计
  }
}

### 6.3 幂等（防重）
对支付、保存等写接口要求 `Idempotency-Key`：

```ts
// shared/idempotency/idempotency.interceptor.ts
@Injectable()
export class IdempotencyInterceptor implements NestInterceptor {
  constructor(@InjectRedis() private redis: Redis) {}

  async intercept(ctx: ExecutionContext, next: CallHandler) {
    const req = ctx.switchToHttp().getRequest();
    const key = req.headers['idempotency-key'];
    if (!key) return next.handle();   // 未带 key 不拦截

    const cacheKey = `idem:${key}`;
    // 抢锁：NX 防并发重复执行
    const locked = await this.redis.set(cacheKey, 'processing', 'EX', 3600, 'NX');
    if (!locked) {
      // 已在处理或已完成，返回缓存结果
      const result = await this.redis.get(`${cacheKey}:result`);
      if (result) return of(JSON.parse(result));
      throw new HttpException('请求处理中，请勿重复提交', 409);
    }
    return next.handle().pipe(
      tap(async (res) => {
        await this.redis.set(`${cacheKey}:result`, JSON.stringify(res), 'EX', 86400);
      }),
    );
  }
}
```

## 9. 分阶段落地步骤

> 每阶段独立可上线、可回滚。**单体阶段即可开始，不依赖微服务拆分。**

### H0：应用无状态化 + PM2 cluster + 健康检查（消除进程单点）

**步骤**：
1. 将 `ChatStreamRegistry` / `EnglishLearningStreamAbortRegistry` 迁移到 Redis（4.1 示例）。
2. `ecosystem.config.js` 改 cluster 模式（4.2）。
3. 新增 `/api/health` 端点（4.5）。
4. Nginx 单后端但配 `max_fails` + `proxy_buffering off`（4.3 简化版）。

**验收**：
- [ ] `pm2 reload server` 期间接口不中断（流式请求可完成）。
- [ ] `pm2 status` 可见多进程。
- [ ] `curl http://host/api/health` 返回 200 含 mysql/redis 状态。
- [ ] kill 单个 Node 进程，PM2 自动拉起，整体可用。

### H1：MySQL 主从 + Redis 哨兵（消除数据单点）

**步骤**：
1. 配置 MySQL 主从（5.1.2），建立复制账号与通道。
2. 部署 Redis 哨兵集群（5.2.2）。
3. 应用 `RedisConfigFactory` 改哨兵接入（5.2.3）。
4. MySQL 前置 HAProxy（5.1.3 简化版）。

**验收**：
- [ ] `SHOW REPLICA STATUS\G` 可见 `Running` 状态。
- [ ] 主库写入，从库可查到（延迟 < 1s）。
- [ ] 手动停主库，HAProxy 流量切到从库，应用写可用（或 Orchestrator 自动提升从为主）。
- [ ] 手动停 Redis 主，哨兵自动选新主，应用 `ioredis` 自动重连。

### H2：多机部署 + Nginx 双活 + 负载均衡（消除单机单点）

**步骤**：
1. 新增 1-2 台服务器，部署应用实例（PM2 cluster）。
2. Nginx upstream 多后端池（4.3），前置云 SLB 或 Keepalived VIP。
3. Nginx 主动健康检查（4.5）。
4. 优雅关闭 + `pm2 reload` 发布（4.4）。

**验收**：
- [ ] 任一应用节点 `pm2 stop`，Nginx 自动剔除，请求转发到其他节点。
- [ ] 任一服务器宕机，整体服务可用（SLB/Keepalived 切换）。
- [ ] 发布期间接口无 5xx（滚动 reload）。

### H3：Qdrant 集群 + 弹性能力（消除向量库单点 + 提升容错）

**步骤**：
1. Qdrant 三节点集群（5.3.1），collection 设分片与副本。
2. 引入熔断器（6.2）封装 LLM/搜索调用。

4. 知识库检索降级链路（6.4）。

**验收**：
- [ ] 单 Qdrant 节点停，集群仍可读写。
- [ ] LLM 服务 50% 失败率时熔断触发，返回降级文案。

## 12. 与微服务方案的关系

本方案不依赖 `微服务架构实现方案.md`，可先行落地（H0–H2 在单体阶段即可用）：

- 本方案的「应用多实例 + Nginx upstream」= 微服务方案的「网关 + 多服务实例」高可用底座。
- 本方案的「MySQL 主从 + Redis 哨兵 + Qdrant 集群」= 微服务各服务数据的 HA 基础（微服务化后每个服务库复用此模式）。
